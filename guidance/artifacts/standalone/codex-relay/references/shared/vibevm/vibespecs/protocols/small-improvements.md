# Small improvements in a future suitable change

<a id="SI-001"></a>
**SI-001 — Explicit adoption supplies standing delegation.**

Apply this topic only when the owning project explicitly adopts it in accepted
human-owned AGENTS or equivalent guidance. Package installation, version updates,
Task Handoff adoption and cross-topic references do not activate it. It covers
small source-change follow-ups in ordinary GitHub Issues in the repository that
owns the correction. That explicit adoption supplies standing same-repository
authorization to discover and automatically include bounded eligible candidates
under SI-004–SI-006 in an otherwise authorized source-changing opportunity.
It does not authorize starting an execution, overriding current Task exclusions
or protected admission boundaries, or controlling another repository/project.
It grants no review, merge, release, label/settings mutation, consumer-adoption
or closure authority.
Retain existing local rules until separately reviewed adoption reconciles them.

<a id="SI-002"></a>
**SI-002 — Existing semantic owners.**

This topic owns candidate capture, discovery, standing inclusion and disposition.
[Contract and decision maintenance](contract-and-decision-maintenance.md#CD-005)
retains accepted reusable-decision promotion and same-change human guidance;
[Task Handoff](task-handoff.md) retains chronological authority, results,
independent acceptance and continuation;
[Requirement Authority](requirement-authority.md) retains proposed versus binding
requirements. References adopt none of those topics. Where not adopted, use the
project's corresponding local rules. Preserve stronger native admission,
Writer/Reviewer identity, protected actions and review requirements.
Under [RA-006](requirement-authority.md#RA-006), an unaccepted suggestion creates
no obligation by itself; here the project's explicit adoption supplies the
delegation. A candidate label alone never does. Exercise that delegation within
its bounds rather than asking the owner to approve each ordinary inclusion.

<a id="SI-003"></a>
**SI-003 — Capture a bounded candidate.**

Record an independently actionable deferred correction promptly as an ordinary
Issue in its owning repository, reusing an existing Issue when appropriate.
Apply the exact label `small-improvement` as the mandatory discovery key through
the project's authorized tracker path. The optional title prefix
`Small improvement:` helps readers but is never a lookup dependency. An Issue
without that label is not discoverable through this mechanism; report unavailable
label capability and use the owner's existing tracker process rather than claim
it is queued. Creating the label itself needs local authority.

Keep enough evidence to understand the problem, intended correction, affected
surface, discovery provenance, why it is deferred and proportionate validation.
Use the Issue body/discussion; no new form, ledger, bot or controller is required.
A label records a candidate, not an accepted requirement or execution admission.
Routine corrections already inside admitted scope need no extra Issue or cycle.

<a id="SI-004"></a>
**SI-004 — Eligibility is semantic.**

Include all reasonably implementable, safe, independently actionable candidates
in the same owning repository that can remain bounded and reviewable alongside
the receiving change. Keep the receiving purpose and each correction clear.
Thematic similarity to the main work and necessity for its primary objective are
not eligibility requirements; an otherwise eligible correction cannot be excluded
merely as unrelated or unnecessary to that objective. Size is risk and contract
impact, not line count. Check dependencies, conflicts, ownership, compatibility,
testability, combined risk and the ability to qualify the combined result through
normal validation and review. Preserve explicit current Task exclusions and
protected constraints.
Urgent incidents, substantial features, unresolved architectural or material
operator-contract choices, protected credential/production work and corrections
with unresolved dependencies or ownership need their ordinary authorized path.
Reassess candidates that grow or become urgent; do not delay required work
indefinitely for a convenient PR. Small package edits still need normal version
classification and release authority.

<a id="SI-005"></a>
**SI-005 — Discover at a suitable source-changing opportunity.**

When preparing an authorized code/source-changing Task, its first source-changing
Step if earlier work was analytical, a relevant Change Request (CR), or newly
commencing another source-changing PR opportunity, inspect open Issues with the
exact `small-improvement` label in that repository. Use the first genuinely
suitable opportunity for pending candidates; do not wait for a thematic match.
Inspect the complete result set, following pagination as needed, and assess the
candidates under SI-004. Include all eligible candidates under the standing
delegation; no per-candidate owner selection or notification before implementation
is required. No suitable candidate is a valid result; it does not block unrelated
work or require batching.

Analysis-only work need not scan under this topic. Do not rescan on every internal
commit, correction or subsequent Step solely as ceremony, or repeat a lookup for
the same already-assessed opportunity without a material change. Refresh on
materially changed receiving scope or new relevant information. There is no
cross-repository scan, periodic audit, queue-empty gate or authority to launch a
Task from the queue. A project's broader separately accepted discovery rule still
applies until explicitly reconciled.

<a id="SI-006"></a>
**SI-006 — Exercise delegation within existing authority.**

Eligible inclusion under the adopted protocol is already delegated. It requires
no separate candidate permission, Task, Step, PR, owner amendment or advance
notification. Identify the included Issue IDs and bounded corrections in the
ordinary receiving records and result; do not invent an approval stage or a
ceremony-only record before implementation.

Preserve explicit current Task exclusions, express revocations of this delegation,
owner holds, protected actions, ownership and the existing execution/admission
binding. New adoption does not retroactively expand already-admitted scope or
rewrite historical charters, terminal executions or acceptance records. Do not
reinterpret an admitted profile or bypass native trust boundaries to make a
candidate fit. A candidate outside this standing delegation needs the ordinary
owner authority and supported admission path; material scope or policy changes
still use the existing Task Decision mechanism. A PR-specific CR cannot grant Task-wide scope
authority it does not own. Discovery does not start another execution or transfer
authority to another repository or project.

Do not disturb an already approved PR solely to add unrelated minor work. Record
it for a future suitable change. A genuine required or urgent correction follows
existing authority and fresh-result review rules, not this deferral shortcut.

<a id="SI-007"></a>
**SI-007 — Integrate and assess the combined result.**

Link each included candidate to the receiving Task, where one exists, and PR;
retain the source Issue's provenance and authorship. State the source Issue IDs
and included corrections in the PR and, where used, the Outcome. Identify any
excluded remainder. Implement together, run normal tests for the changed behavior
and coupled paths, and use one independent PR review of the combined exact
result. No separate execution cycle, PR, approval or ceremony-only commit is
required for each tiny Issue. Applicable checks, changed-head rereview, package
versioning, Draft/Ready and protected boundaries retain their existing meaning.

The receiving result records what was delivered, checks, warnings and remaining
work. Selection, scheduling, a pushed commit or successful tests do not prove
accepted integration. Preserve the project's normal merge and closure ownership;
links or automatic closing keywords cannot bypass it.

<a id="SI-008"></a>
**SI-008 — Keep unfinished work discoverable.**

Keep the source Issue open and traceable until actual accepted integration is
evidenced, then reconcile it through authorized closure with the receiving PR
and integrated revision. Scheduling or transfer alone does not close it as fixed. When a correction lands
elsewhere, link the accepted result and reconcile the source Issue’s remaining
criteria and any distinct required installed outcome. Reuse sufficient acceptance
evidence without duplicating implementation or fabricating retrospective review;
[TH-018](task-handoff.md#TH-018) applies where Task Handoff is adopted.
Retain the discovery label while work remains pending, including while scheduled,
unless separately accepted local tracker rules require a different label lifecycle;
that binding must preserve discovery of unfinished work through explicit links.

For each deferral, record a concrete eligibility, safety, dependency, ownership,
reviewability or current-authority reason and its next suitable opportunity or
ordinary authorized route; retain discoverability. Topic mismatch, non-necessity
to the main goal or a preference to avoid using the standing delegation is not a
deferral reason. If the receiver is cancelled, drops the correction or delivers
only part, record what happened,
retain or restore pending discovery and identify exactly what remains. Do not
mark a partially delivered Issue fixed. If a candidate is duplicate, superseded
or no longer needed, record evidence and the surviving reference or reason, and
use the project's authorized tracker disposition without claiming a fix occurred.
Age alone never closes or executes it. No suitable opportunity can leave it
pending; urgency or increased scope routes it to ordinary authorized work.

The [usage guide](../guides/small-improvements.md) illustrates the standing
delegation, lookup and separately owned consumer migration. The protocol owns
the automatic inclusion rule; examples add no authority.
