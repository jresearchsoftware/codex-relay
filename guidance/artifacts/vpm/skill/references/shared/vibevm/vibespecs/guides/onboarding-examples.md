# Worked project onboarding examples

These fictional projects exercise the [operator procedure](onboarding.md).
They are contributor self-checks of the procedure, not live consumer onboarding,
independent assessment, native client tests or evidence that settings were changed.
Project names, decisions, revisions, observations and results below are invented
test inputs. `VERIFIED` means supported by the stated hypothetical observation;
it never describes an inspection of a real external project by these examples.
`READY` is a verdict for the explicitly chosen scope, not a sixth evidence state.

Each walk starts with the same ordinary request: **“Onboard this project to
Shared Governance.”** The operator reads the project's accepted authority,
discovers the relevant paths, recommends choices, gets owner disposition and
separates authorized file work from protected setup. A plan can be complete while
onboarding readiness remains unverified or a gap remains unresolved.

## 1. New manual-only GitHub library

**Discover.** Birch is a new Windows/Linux library with an owner-approved charter,
one maintainer account, ordinary external contributors, a passing compilation/test
workflow and no release publisher. Its owner has authorized investigation and a
proposed file diff only. The operator reads the accepted root instructions,
workflow triggers and one successful ordinary-PR run; no existing topic adoption
or VibeVM lock is present. The owner has not selected a development workflow.

**Recommend and choose.** Offer a PR source path or a documented direct path with
its trade-offs; the owner selects PR source development and manual execution.
Assess all nine topics for relevance without adopting them by availability:

| Owner disposition | Topics and reason |
| --- | --- |
| Select | Proportional controls, requirement authority, task handoff and GitHub repository governance: control choices, accepted requirements, manual Task/result routing and source workflow are needed now. |
| Select | Context loading: preserve contributor entrypoints while routing full relevant material only when triggered. |
| Defer | Independent review methodology and contract/decision maintenance: keep the existing substantive assessment and contract rules while the owner considers these additional topics. |
| Decline for this scope | Package versioning: Birch ships no package or versioned distribution; its existing release rules remain authoritative if that changes. |
| Not applicable | Producer self-adoption: Birch does not author the governance it consumes. |

The owner chooses a reviewed exact package pin and native VibeVM loading for the
five selected topics. The package supplies all available files; the human-owned
route explicitly adopts only the chosen five. An existing local rule requiring
owner authorization for signing-key use remains local and unchanged.

**Plan and authority.** Prepare one candidate diff covering the dependency, lock,
materialized slot, boot route, selected-topic declarations and manual Issue/result
binding. Record how existing contributor PRs remain startable. File application,
package installation and adoption still need the project's separate admission
and review. Recommend squash and disposable-branch deletion if compatible;
protection-setting changes are a separate owner/admin action, outside this diff.
Do not require Relay, a new bot or another authenticated reviewer identity.

**Read-only checks.** Inspect proposed manifest/lock/slot identities, compare the
slot to the selected immutable package, and follow root → INDEX → boot → selected
protocol links. Check Windows case/path handling and inherited/nested instructions.
Read current merge options, classic protection, inherited active rulesets,
bypass scope and ordinary-check reporting identity through authorized access.
An existing independent human assessment can be attributed through the owner
account; it supplies no distinct native GitHub approving identity.

**Handoff.** In this specimen, existing compilation/check evidence is VERIFIED;
the candidate routing is VERIFIED as static file evidence. Adoption and native
materialization are DEFERRED: source is the investigation-only admission; impact
is that Birch still uses local rules; responsible owner is the maintainer; next
authorized action is disposition and a separately admitted reviewed file change.
Manual PR work can continue under local rules now. The onboarding plan is
complete; selected-topic operation is not READY until that authorized setup and
readback occur. No live Codex or ChatGPT traversal has been demonstrated.

## 2. Living evidence repository with routine direct-main updates

**Discover.** Atlas maintains dated compatibility measurements. Its accepted
instructions authorize non-force routine evidence refreshes directly on `main`;
a changed recommendation needs substantive assessment and owner disposition.
Read the dated-source format, recent routine commits and material-change record.
The owner asks to assess onboarding while preserving that distinction.

**Recommend and choose.** Select proportional controls, requirement authority,
GitHub repository governance and context loading. Retain the accepted lightweight
commit/review mechanism; defer task handoff and independent-review methodology
pending a concrete need. Decline package-versioning for this unversioned evidence
scope; self-adoption is NOT APPLICABLE. Recommend contract/decision maintenance
for changes to recommendations; the owner defers it and retains local policy.
Choose a pinned package and an explicit read-only manual route to selected full
protocols; no claim of native VibeVM boot or client integration is made.

**Plan and authority.** The owner separately admits a narrow instruction/link
change through the existing review route. Keep primary sources, dates,
uncertainty and commit explanations. Do not propose `Restrict updates` or a
PR-only rule that would prevent the accepted refresh path. No settings changes
or new review machinery are authorized.

**Read-only checks.** The specimen includes owner readback of accepted instructions
and pinned files after the file change, plus current classic/ruleset evidence
showing non-force direct updates remain possible and important history/deletion
is protected. Trace a corrected measurement to its source and validation; trace
a changed general recommendation to the durable assessment/Decision route.
Check that no selected protocol silently imports the deferred task mechanism.

**Handoff.** Manual selected-topic access and these two paths are VERIFIED and
READY for the stated manual scope. Codex/ChatGPT instruction loading and native
boot are NOT APPLICABLE because the owner selected neither. A future client
route is DEFERRED, owned by Atlas's maintainer, with no impact on manual use;
its next action would be a separately authorized client-binding change. Recheck
affected settings only after relevant policy, writer, permission or drift changes.

## 3. Mixed source, retained branches and generated publication

**Discover.** Cedar uses PRs for source, retained `integration` and `release/1.x`
branches, and a generated distribution branch written directly by a qualified
publisher. Frozen tags identify releases. Read accepted path rules, publisher
contract, existing no-overwrite boundary and one ordinary source/release record.
The owner wants readiness recommendations, not publisher replacement. In this
fictional project, a standing release-sync PR uses same-repository `release/1.x`
as its head and `main` as its base; the owner intends to merge it while retaining
that head for further maintenance. The retained branch's mere existence would
not establish the automatic-deletion trigger.

**Recommend and choose.** Select GitHub repository governance, proportional
controls, requirement authority, task handoff and package-versioning. Retain local
publisher identity, credential handling, release admission and recovery. Defer
additional context/review/contract topics while existing local rules serve those
domains; self-adoption is NOT APPLICABLE to this downstream package consumer.
The owner chooses a pinned native dependency and explicit selected-topic route.

**Plan and authority.** Prepare a reviewed file-adoption plan preserving both
paths. For that planned merged-PR head usage, recommend compatible deletion protection
or keeping auto-delete off. GitHub's setting concerns merged PR head branches;
for retained branches not used that way, establish the predicate before calling
auto-delete a gap or recommending a change solely on that basis. Scope branch/tag protections to actual refs and authorized
writers; inspect whether a publisher bypass would also bypass immutability.
No broad bot exemption, global PR-only rule, tag rewrite or credential change is
implied. Owner/admin setting work and publisher changes require separate authority.

**Read-only checks.** Examine source PR checks and assessment at its exact head;
match required names/triggers/identity to actual successful runs. Follow a release
from accepted source to artifact identity, frozen closure and existing tag guard.
Read current active inherited/ref rules, exclusions, bypass modes and retained
branch coverage. Verify native source/lock/slot/route consistency independently of
the install return code. Do not test protection by overwriting or deleting refs.

**Handoff.** Static selected-topic routing and ordinary source checks are VERIFIED.
GAP: hypothetical current setting/ref-rule readback shows auto-delete enabled
and no applicable deletion protection for `release/1.x`; the release-sync PR record
establishes its same-repository head usage and planned merge. The supported
retained head is therefore exposed to automatic deletion after that merge;
no deletion has been observed or tested; responsible owner is Cedar's repository admin; next
authorized action is owner disposition of disabling auto-delete or protecting the
retained branch, then authorized application/readback. Publication bypass details
are UNVERIFIED where hidden by current access; the release owner must supply
authorized evidence before a publication-readiness claim. The plan is complete,
but combined source/publication onboarding is not READY. Source policy acceptance,
settings enforcement, publication and downstream adoption remain separate claims.

## 4. Existing consumer with duplicated governance and a semantic gap

**Discover.** Delta already pins a governance package but its root instructions
still hold canonical local control rules. Read the complete accepted local slice,
its applicable Decisions, original extraction evidence and existing client routes.
The reusable local requirement “reuse sufficient exact-candidate proof before
adding another gate” is absent from Delta's old pinned shared version. A local
production two-person credential rule is an explicit consumer-owned exception.

**Recommend and choose.** Recommend updated proportional-controls plus requirement
authority and context loading; the owner selects them. Defer task/review/contract
topics while local authority remains canonical; decline GitHub guidance for this
internal non-GitHub scope and package-versioning for this application-only change.
Self-adoption is NOT APPLICABLE. Pin a later independently accepted package only
after establishing that its canonical content repairs the reusable omission.

**Plan and authority.** Map each local obligation, trigger, exception, cost and
route to the chosen shared source or a justified local owner. The owner separately
admits a migration candidate: dependency/lock/native routing update and removal
of genuinely duplicated canonical rules together. Keep the production credential
rule local with its ownership rationale. Installation alone transfers no authority;
the current local canonical rules remain effective until the migration is accepted.

**Read-only checks.** Compare the whole mapped baseline with the replacement and
walk a new consumer without residual Delta rules. Follow root/nested/Codex routes
and any supported ChatGPT binding separately; compare lock identity, slot content
and generated boot. Confirm the native static INDEX entry reaches the intended
conditional protocol routes without claiming native dynamic-include behavior.
Check removal leaves neither an uncovered obligation nor two canonical owners.
Delta also uses ChatGPT for read-only review. Its proposed pinned-slot projector
check finds current desired Instructions/custom/binding/receipt, but no owner
export or live settings readback exists. Preserve unknown live rules; do not
overwrite settings or equate generated consistency with client readiness.

**Handoff.** GAP: until a qualifying accepted repair exists, the source-to-shared
map identifies an omitted reusable obligation; impact is a weakened control-cost
decision; responsible owner is the shared producer for repair and Delta's owner
for migration; next authorized action is producer disposition and independent
acceptance of a later version, followed by Delta's admitted migration. Keep the
local canonical slice meanwhile, without calling it a successful extraction.
If the repair is available, candidate coverage may be VERIFIED statically, but
acceptance/application remain DEFERRED to Delta. Onboarding planning completes;
the proposed ownership transfer is not READY merely because leftover rules work.
ChatGPT loading/settings are separately UNVERIFIED: source is absent live
evidence; impact is that this review path cannot be promised; Delta's client
owner must authorize application/readback and demonstrate the needed access.
That gap need not block a separately accepted and verified manual route.

## 5. Non-GitHub, non-Relay manual route

**Discover.** Elm uses a private Git server, a local change tracker and manual
review. Its accepted binding unambiguously identifies change records, authorized
execution, exact-result assessment and the durable result-publication location.
No Codex, ChatGPT, VibeVM runtime or Relay is part of its supported workflow.

**Recommend and choose.** Select task handoff, proportional controls and requirement
authority using the existing tracker binding. The owner chooses pinned readable
protocol files and manual links rather than native loading. Defer context loading,
independent-review methodology and contract/decision maintenance while local rules
remain in force. Package-versioning is declined for this scope, self-adoption is
NOT APPLICABLE and GitHub governance is NOT APPLICABLE to this host.

**Plan, checks and handoff.** Under Elm's separate admission/review, plan explicit
adoption text and links; do not import GitHub APIs, Relay schema or credentials.
The specimen's post-change readback verifies file provenance, full selected-topic
access, tracker identity, one manual ordinary-change path and attributable result
publication. Those are VERIFIED and READY for the manual scope. Native lock/boot,
GitHub settings and live client traversal are NOT APPLICABLE. An unresolved local
publication permission would instead be UNVERIFIED, owned by Elm's tracker
administrator, blocking result-publication readiness until authorized readback.

## 6. Protected configuration visibility is missing

**Discover and choose.** Fir's owner selects a manual GitHub PR scope after the
same authority/topic discovery as Birch. File reads and ordinary check history
work, but classic protection returns an ambiguous 404; inherited rules or bypass
actors are hidden. A visible `protected` flag cannot fill those gaps.

**Plan and check.** Recommend the minimal file plan and list required enforcement
evidence separately. Reuse current owner UI exports/readback if sufficient; do not
change accounts, request broader tokens, upgrade plans or mutate settings to test.
The owner may separately authorize admin inspection, accept a concrete risk with
manual controls, narrow the chosen scope, or defer setup.

**Handoff.** File accessibility and existing checks are VERIFIED. Enforcement is
UNVERIFIED: source is the inaccessible/incomplete API surface; impact is unknown
coverage of accepted history, review and writer invariants; responsible owner is
Fir's admin; next authorized action is existing authorized UI/API evidence and
owner disposition of the resulting gap. Admin inspection is DEFERRED by owner
choice. The plan is complete; enforced-profile readiness is not READY. If a
narrow manual profile is later accepted, report readiness only for that profile.

## 7. Install/update alone is not an onboarding request

Grove's routine dependency update materializes all nine topics. No owner asks for
onboarding or new adoption. The operator does not start this procedure or inspect
repository settings. Existing adopted topics and local rules continue through
their accepted routes; newly available topics remain passive. Any ordinary update
checks follow Grove's existing update contract. “All files installed” establishes
neither adoption nor readiness. Onboarding is NOT APPLICABLE to this event, and a
future explicit request starts with current authority and decision-relevant facts.
