# Shared governance and Relay product bindings

This repository deliberately adopts Shared Governance **12.5.0** as the single
canonical source of its portable development governance. The immutable
producer is
`f51fd0ab22ff61fab48bd1e5af96918d77af1ec6`; the distribution is
`e19ceeaa3ffe608fe078d37171ddd7cd5a940dda`. Root [AGENTS](../AGENTS.md)
explicitly adopts all eleven complete applicable protocols. Their conditional boot
pointer selects reading, never individual clauses. The authored
[product Skill](../packages/codex-relay/skill/SKILL.md) preserves the product
bindings below. Native delivery reads complete shared protocols from the
consuming project's reviewed lock and selected Shared slot through its generated
`references/shared-protocols.md`; standalone includes the attributed immutable
12.1.0 snapshot. Consumers deliberately select and adopt their own compatible
Shared dependency. No fixed bundled native route supersedes that selection.
The historical
[Task #108 analysis](task-handoff-methodology-analysis.md) and earlier
[2.1.0 assessment](vibevm-semantic-coverage.md) remain evidence, not active policy.
The bounded [migration assessment](relay-skill-compatibility.md#project-migration-from-500-through-700) records semantic dispositions; it is not a second rule owner.

## Native authority and compatibility

Task Handoff owns portable charter chronology, execution-cycle Step, minimal
handoff, bounded correction, preservation, results and continuation. Relay's
[authority contract](../contracts/README.md#github-native-task-authority) owns
Issue #N, trusted v4 Decisions, immutable admission, protected reservations and
native identities/body digests. Writer alone allocates Step at consumed owner
launch. The Issue's valid Step position is numbering input reconciled with
successful admitted history; labels/titles project the durable result and grant
no execution authority. TH-002/006's ordinary dispatch needs no
extra Decision merely certifying that same start; the native authenticated
command and immutable admission still implement the product trust boundary.
Issue openness alone starts nothing. Current Node admits only v4; exact older
operations preserve selected authority, Step and recovery/publication bindings
through frozen original source. Historical Requests supply no current execution
fields or extra migration gate. A selected trusted v3 Decision remains bounded
provenance for an admitted v4 result; fresh admission requires every effective old
field to be replaced by later active v4 authority. Fully shadowed existing evidence
needs no new Decision or formal supersession. Shared adoption neither renumbers
history nor qualifies an installation.

The canonical [manual](../packages/codex-relay/skill/references/workflow.md)
retains automatic, admitted-manual and explicitly authorized standalone routes.
Manual operation does not fabricate admission or Writer provenance. The full
copyable admitted prompt and profile remain available; its snapshot is subordinate
to live canonical authority. Exact thread-title/readback is a client binding.

one canonical Outcome. Ambiguous PR creation cannot fall back to the Issue.
Shared TH-014–017 covers actual complete/mixed results without requiring new
multi-PR orchestration; extending Relay's unique-artifact runtime capability
requires separate product authority and qualification. No-PR analytical or
qualification results use the Issue without an artificial PR or commit.

## Small Improvements binding

Relay development adopts the complete [SI-001–SI-008 protocol](../vibevm/vibedeps/org.jresearch.ai.development-governance/12.5.0/vibevm/vibespecs/protocols/small-improvements.md)
through Task [#273](https://github.com/jresearchsoftware/codex-relay/issues/273),
effective after normal independent exact-head acceptance and integration of
this adoption. This supersedes the related-candidate and advance-notice
practice under Tasks #230 and #244 for future opportunities. Preserve original
admissions and explicit exclusions or revocations. The Relay product Skill
does not adopt SI for consumers.

At the first genuinely suitable otherwise authorized source-changing Task,
its first source Step after analysis, relevant CR or newly commencing PR,
inspect all pages of open Issues matching the exact repository and label:

```text
repo:jresearchsoftware/codex-relay is:issue is:open label:small-improvement
```

Assess each candidate under SI-004 and automatically include all eligible
same-repository corrections, including unrelated topics. Consider combined
risk, ownership, compatibility, dependencies and reviewability. Use the
ordinary receiving records and result for Issue IDs, bounded corrections and
provenance. Standing delegation needs no per-candidate permission, Task,
Step, PR, owner amendment or advance notice.

For native execution, discover while preparing the effective receiving scope.
Use its charter and any applicable trusted Decision or CR when defining that
scope for the ordinary launch. Writer verifies the native owner launch and snapshots its actual
effective authority. It neither scans the backlog nor treats a label, source
Issue or ordinary comment as scope or admission authority. If discovery comes
after admission, respect the exact snapshot and any express exclusions. Use
the existing authorized path for a genuine material scope change, or defer.
A PR-specific CR cannot grant Task-wide authority. Standalone work exercises
the same delegation within its otherwise authorized scope and records
inclusions in the receiving PR or Task record. Preserve protected operations,
actor separation and already-approved PRs.

| Receiving situation | Application |
| --- | --- |
| Newly commencing PR with two bounded same-repository fixes, including an unrelated typo, and a third requiring protected deployment | Include both bounded fixes in the normal result, link the source Issues and record the protected candidate's ordinary authorized route. |
| First source Step after analysis or relevant CR with an express exclusion | Assess the queue at preparation, honor the exclusion and record the concrete deferral. |
| Analysis-only Task or inner correction with unchanged scope | Skip the scan. Refresh only after a material change in receiving scope or relevant information. |
| Already admitted execution or already approved PR | Preserve its bounds. Defer ordinary additional work to the next suitable opportunity. |
| Empty or unavailable queue | Proceed with authorized work, reporting unavailable discovery or label capability. |

Capture bounded deferred work through authorized Issue and label tools. Use
`small-improvement` as the lookup key and keep unfinished or partial work open
and discoverable. Record why each deferral remains ineligible and its next
suitable opportunity or ordinary route. For included work, link each source
Issue and remainder in the receiving PR and Outcome using neutral references.
Run normal checks and one independent review of the combined exact head.
Reconcile closure through normal authorized continuation after accepted
integration and any separately required operational verification. A duplicate
or superseded candidate needs evidence and a surviving reference or reason.

There is no cross-repository or periodic queue scan, queue-empty gate, new
runtime, convening of a new Task from the queue or separate approval stage.

## Closure names and Relay authoring

Shared TH-026 pairs `close-on-final-result` with `close-authorized` and
`close-on-condition` with `keep-open`. Each pair means the same thing in
Shared Governance. Fresh Relay authoring uses exactly one existing spelling in
the charter or applicable Task-scoped trusted Decision. The current JavaScript
and Rust readers and authority schemas require `close-authorized` or
`keep-open`. See [closure authoring](../contracts/README.md#closure-policy-authoring)
for final and intermediate PRs, verified continuation and no-PR completions.
Preserve any admitted literal, meaning and hold through its original binding.

[Proposal #294](https://github.com/jresearchsoftware/codex-relay/issues/294)
tracks a separate product change. A future alias migration requires Relay
authority, JS/Rust/schema compatibility and runtime qualification, and an
assessment of changed product guidance and its release. A project can prefer
the new spellings when its accepted guidance, authoring client/Skill and
applicable runtime all support them. This project-only adoption keeps the
10.0.0 product deliverables byte-identical.

The previously qualified legacy product flow remains usable only for actually
qualified legacy combinations: neutral PR/squash references, explicit

[closure authoring](../contracts/README.md#closure-policy-authoring),

and the installed version-specific contract.

to actually qualified legacy combinations and behavior. It remains permitted
pending the first Relay release implementing and qualifying the new closure

Shared 10.0.0 publication starts no clock. Record the actual release/source,
publication event and derived deadline in the existing Issue/release chronology
when verified; no trigger date is asserted here. Removal requires a separately
accepted future Shared release no earlier than the window's end; expiry does not
automatically remove the fallback. This exception extends to no other protocol,
consumer or unknown version. The product floor is not blanket compatibility proof.
