## Exact retirement boundary

The reusable body of [Relay's proportional-controls section](execution-policy.md#proportional-controls-and-operator-usability)
can become a stable route to the complete shared procedure. Retain local
bindings for canonical Task/CR authority, `OWNER_DECISION_REQUIRED` and full G1,
Writer/Reviewer separation, protected operations and exact-candidate acceptance.
Adopt requirement-authority for relevant provenance decisions without copying
its procedure back into local policy.

In AGENTS minimum sufficient ceremony, retire the repeated free-hardening,
cost-bearing-authority and simplest-path review prose now supplied by the
package. Also retire the generic least-complexity, independent-purpose and
same-invariant repetition prose only after routing explicitly reaches G2 when
an additional mandatory or ceremonial step is proposed. Retain Relay's choice
of live Issue/CR, PR diff, exact Git facts, native checks and one Outcome as its
existing evidence surfaces. Keep the same-Task documentation rule, native CI
publication cadence, targeted correction/full candidate checks, independent
judgment, decision promotion, optional hooks and warning disposition local.
Those procedures were not extracted or qualified as shared duplicates.

The whole passive payload is installed; applicability is conditional reading,
not selective installation. **Package-versioning is not adopted by this change.**
Its boot explicitly requires a separate project-owned topic adoption. Its
presence does not replace Relay's release cadence or existing versioning policy.
The package has no dependencies, executable capabilities or native Skills.

## Same-content baseline and evidence limits

An exact-SHA Git vendoring approach can supply the same seven payload files,
their receipt and the same short conditional route. Its source review and policy
decisions would be identical; a native Skill wrapper could provide discovery for the same prose
under a separately authorized design. This change creates no Skill projection.
Native Skill discovery is not an advantage uniquely supplied by VibeVM, and
comparing different prose or methodology would not isolate distribution value.
The [accepted baseline criteria](vibevm-governance-design.md#comparison-and-next-experiment)
remain useful: compare deliberate update effort, diff size, extra binary/cache/
lock state, reproducibility, overlay preservation, offline reads and rollback
for the same content. No cross-repository synchronization or context-saving
benefit has been measured by this source comparison.

The integrated disposable Git fixture exercised the candidate route snapshot;
these are observed file and Git results, separate from source walkthroughs and
the final candidate's required checks:

| Fixture | Observed evidence | Limit |
| --- | --- | --- |
| Git-only transport | All eight distribution files, including the receipt, copied byte-for-byte: **24,390 UTF-8 bytes**. Separate fixture commit and local clone retained exact equality. | No maintenance-effort or superiority measurement. |
| Native Skill comparison | The same eight files plus a **477-byte synthetic native Skill wrapper**; relative links resolved and a separate fixture commit/clone retained equality. | Disposable comparison only; no production Skill projection, client discovery or model behavior tested. |
| Clean local clone/offline reads | A real `--no-hardlinks` local clone, absent `.vibe`/cache, new HOME, empty PATH and forbidden socket connections allowed plain Python reads of all **three INDEX entries**, both adopted complete protocols and all three managed entrypoint blocks. | File readability and link traversal; no claim that a model loads or follows the routes. |
| Distribution overhead | VibeVM's native slot inventory adds **1,128 bytes**, alongside project manifest/lock/generated INDEX state. | Byte inventory only; no measured operating cost or comparative task performance. |
| Git rollback/removal | Reverting the disposable atomic migration restored the exact complete starting tree, local controls, original dependency-free graph and INDEX, and removed the installed slot. | Disposable Git lifecycle proof; package update lifecycle and production/client rollback not tested. |

Standalone text walkthroughs supply bounded semantic evidence. For an unchanged
candidate with sufficient independent proof, P 80–92 rejects another ceremonial
step absent a justified purpose, while a changed candidate or distinct invariant
requires its necessary proof. For an internally chosen response-size cap that
breaks an authorized supported review path, P 96–117 and A direct investigation
and a smaller safe repair without reauthorizing the arbitrary cap. If removing
that cap would discard a demonstrated memory, credential or trust invariant,
the same procedure preserves the protection and requires authorized disposition
for any unresolved material change. These are applications of complete shared
text and scenario facts, not observed model compliance.

Committed file readability, CLI materialization, route generation and actual
model traversal are separate claims. An offline file/route check can establish
that an ordinary clone needs no session-time binary, cache, registry, network
or extra owner action; it cannot establish which instructions a model loads or
follows. This assessment does not launch another model execution, qualify live
ChatGPT client instructions, or claim measured task performance, production
readiness or warning completeness. Native checks and the integrated acquisition,
lifecycle and rollback evidence remain their own records; independent acceptance
must review the exact final candidate and required execution-warning surfaces.
