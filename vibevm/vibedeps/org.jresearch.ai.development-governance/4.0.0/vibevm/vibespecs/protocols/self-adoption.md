# Producer self-adoption

## Applicability and accepted authority

<a id="SA-001"></a>
**SA-001 — Explicit producer adoption.**

Apply only where a producer consumes some guidance or agent Skills it authors,
and where the project explicitly adopts this topic. Other repositories ignore
it. Installing/updating a package or reading a new topic does not activate it.
Retain the owning project's authority, applicability and local overlays; this
protocol grants no execution, review, merge, publication, installation,
consumer-adoption or closure permissions.

<a id="SA-002"></a>
**SA-002 — Freeze independently accepted guidance.**

Develop and independently assess candidates under identifiable, independently
accepted source-main guidance. Freeze its identity for the effort or review as
appropriate. Source acceptance and public package publication are distinct;
accepted source can govern its producer before publication unless the producer's
explicit local product contract requires publication. Downstream consumers own
their adoption and compatibility decisions.

<a id="SA-003"></a>
**SA-003 — Candidate separation and client limits.**

Candidate rules, root/nested AGENTS, generated boot and Skill projections are
proposals. They may be authored, installed, regenerated, diffed and tested, but
must not silently govern the session developing or reviewing that candidate.
Use a supported explicit launch/task binding to accepted source, independent of
candidate instructions' own authority claims. A prompt can address accidental
candidate-rule activation where the client's tested instruction hierarchy
supports it; it cannot override system/developer rules or provide OS/sandbox
isolation against arbitrary candidate code. Distinguish preloaded text from
executed commands. Qualify relevant root/inherited/nested behavior, conditional
reads and continuation, and disclose unavailable clients or evidence.

<a id="SA-004"></a>
**SA-004 — Qualified manual workflow.**

Prefer the cheapest adequately qualified manual workflow. A separate accepted
snapshot is an alternative where needed, not a universal requirement. State
remaining startup limitations instead of claiming enforcement from a sentence
in candidate-controlled prose or a synthetic marker response alone.

## Native source-controlled ready state

<a id="SA-005"></a>
**SA-005 — Native tools and preserved overlays.**

Prefer the host's ordinary package manager/materializer or native Skill
installer. Use stable inputs, exact provenance, conditional/JIT routing, safe
rollback and preserved project overlays. Do not prescribe a custom resolver,
mandatory registry/service, global policy engine, update ledger, arbitrary model
gate or universal PR policy. A demonstrated tool gap requires a bounded
project-owned disposition before replacing an already verified mechanism.

<a id="SA-006"></a>
**SA-006 — Committed ready state and integrity.**

For an adopted source-controlled producer layout, commit materialized
dependencies and generated boot/agent routes with source changes in the same
reviewed candidate. A clean accepted checkout contains functioning applicable
guidance without downloads, a materializer or bootstrap execution. Ordinary
execution reads those accepted files; deliberate development/maintenance runs
the materializer. Pull/checkout advances source and projection together.
Existing CI detects missing, stale, conflicting or mismatched source, slots,
lock and routing; an install/check exit code alone is insufficient where a
demonstrated integrity gap exists. Reuse exporter/Git evidence before adding
another framework or manual hash exercise.

<a id="SA-007"></a>
**SA-007 — Same-change generation and exact-head assessment.**

Author and materialize before independent exact-head review. Assess source,
generated diff, semantic coverage, accepted authority and applicable validation
together. Changed heads need applicable fresh qualification and independent
assessment; earlier exact-head acceptance does not transfer. No special
just-before-merge hook or separate post-publication adoption PR is required.

## Candidate tests, failure and recovery

<a id="SA-008"></a>
**SA-008 — Bounded candidate probes.**

Use structural checks and simple scenarios by default. Where model behavior
matters, feed candidate guidance to an isolated disposable probe. This tests
future rules without activating them in the producer/reviewer session and
supplies implementation evidence, not independent acceptance. No persistent
TEST service or extra approval ceremony is required.

<a id="SA-009"></a>
**SA-009 — Failure and recovery.**

Do not activate partial/corrupt materialization; preserve accepted guidance.
Detect producer/source/slot/index mismatches using existing tooling and exact
Git evidence. Retry through the supported path after recovery. Ordinary Git
restore/revert is rollback for committed projections; frozen releases are not
rewritten. A publication outage does not revoke independently accepted source.
Report concrete gaps and seek the owning project's disposition when supported
tools cannot meet its contract, without silently changing protected boundaries
or adding material operator work.
