# Development governance

For proposed security, validation or operator controls, read the full
[proportional-controls protocol](../protocols/proportional-controls.md),
including when assessing behaviorally free security hardening. Unrelated tasks
do not require reading it. Apply shared guidance within the owning project's
current scope and authority; it grants no task, publication, review or
consumer-adoption permissions. Consumers separately review and pin updates.

When deciding whether an earlier requirement binds newly authorized work,
read [requirement-authority](../protocols/requirement-authority.md) when relevant
under the owning project's adopted guidance. Proportional-controls routes its
own relevant provenance decisions there; a project may separately adopt that
common rule for other domains. It does not activate a contract-review flow,
supersede local authority or require provenance work on unrelated tasks.

For package lifecycle work, read [package-versioning](../protocols/package-versioning.md)
only when the owning project has explicitly adopted that topic through its
human-owned AGENTS or equivalent policy. Installing or updating this package
does not activate that protocol or replace pre-existing local versioning rules.
Newly adopting projects select their route in their own accepted guidance;
unrelated tasks skip it. Conditional reading does not selectively install clauses.

For governed task execution, handoff or continuation, read
[task-handoff](../protocols/task-handoff.md) only when the owning project has
explicitly adopted it through human-owned AGENTS or equivalent guidance.
Installing/updating this package does not activate the topic or replace local
Task authority, authorization, review or execution mechanisms. Adopted bindings
implement its shared Step semantics and selected acceptance strategy. Unrelated tasks
skip it; client adapters and product-version compatibility remain project-owned.

Where a producer consumes guidance or Skills it authors, read
[self-adoption](../protocols/self-adoption.md) only when its owning project has
explicitly adopted that topic. Develop/review under identifiable independently
accepted source-main guidance; candidate rules remain proposals. Ordinary native
materialization, committed ready files and conditional reading preserve project
overlays and local authority. Other repositories and unrelated work skip this
topic; package installation or update does not activate it.

For GitHub repository onboarding, workflow or protection-policy decisions, read
[workflow-aware repository governance](../protocols/github-repository-governance.md)
only when the owning project explicitly adopts that topic. Preserve its accepted
PR, direct-main, publication and mixed paths; installing/updating guidance neither
applies settings nor grants permission to change them. Existing local policy
remains authoritative until reviewed adoption. Unrelated tasks skip this topic.
