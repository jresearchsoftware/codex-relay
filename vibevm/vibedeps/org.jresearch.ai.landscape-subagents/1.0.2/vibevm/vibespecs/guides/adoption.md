# Assessing adoption of landscape-subagents 1.0.2

This is setup guidance, read for a consumer's explicit adoption/update request.
Installing the package or reading its boot does not adopt it, grant delegation,
or authorize client configuration changes. A project with adequate existing
instructions may need no change. Global reference, project copy and a pinned
VibeVM dependency are integration choices; choose under local authority.

For this versioned-flow choice, the consumer deliberately selects the installed
version through its own normal dependency process. Publication and consumer
adoption are separate decisions; the temporary local install test is a fixture,
not a consumer migration recipe. Preserve active global/project overrides,
existing instructions, task profiles, allowlists, cost limits and review rules.
Avoid loading both a separate policy copy and this projection unnecessarily.

After a separately authorized integration, applicable human-owned instructions
can explicitly adopt the flow. For example, adapt this text to the real consumer:

```markdown
We explicitly adopt the installed landscape-subagents flow 1.0.2.
When Subagents is On and this task and runtime permit delegation, follow its
conditional boot and full policy before substantial work. This requests useful
proactive delegation at every supported parent effort, without a helper quota
or a requirement for Ultra. Identify useful independent branches, strongly
prefer parallel assignments within capacity, and reassess as work changes.
Choose each helper's model and effort within our allowed choices. Preserve
Subagents Off, task permissions, the parent's profile and our review boundaries.
Keep the adopted version stable for the admitted task.
```

The VibeVM-generated root instruction route points to the installed boot through
the native INDEX. Verify that route and actual file accessibility in the target
client; do not assume an external file is automatically injected. Native 1.0.7
can emit a static INDEX entry for a declared dynamic boot; its explicit adoption
condition remains in the boot text. No second loader or boot command is needed.

## Runtime and configuration boundaries

Read the [dated runtime evidence](runtime-evidence.md) when assessing client
support. It inspected Codex CLI 0.160.0, commit
`a956835d020762cb2b570053af06f643a11c0ecc`, with source tests inspected rather
than executed. It establishes no universal current desktop/server behavior.
Instruction adoption does not alter the runtime's developer-message mode.

Check actual supported tool parameters and allowed profiles. Optional custom
agent TOML files are useful only when a stable role is desired. A fixed custom
role's model/effort can take precedence over spawn/default resolution; do not
assume spawn arguments override it. Use a suitable role or general helper.
If the runtime cannot choose profiles, use supported inheritance and disclose
the limitation. A profile written in an assignment is not proof of runtime
selection. A published model list does not prove session access.

A supported runtime-policy override is a separate optional consumer assessment,
not a prerequisite. The inspected `multi_agent_mode_hint_text` replaces mode
text; it is not `proactive = true`. Do not change a running task's configuration,
launch a separate CLI/Relay worker, or alter the parent's profile to bypass a
restriction. Any configuration change needs consumer authority and verification
in that actual client and a fresh session.

## Verify separately in the intended consumer

1. Inspect the instruction sources loaded in a fresh session, active override
   files, generated route and policy access. Check instruction-size limits if
   loading fails. Installation alone is insufficient evidence.
2. With Subagents On at a supported non-Ultra parent effort such as medium,
   use a substantial task with useful independent branches. Look for bounded
   parallel assignments and overlap with the parent's work, not a spawn count.
   Zero helpers remains valid when useful independent work is absent.
3. Give distinct simple retrieval and difficult analysis branches. Inspect
   requested child model **and** effort against actual exposed runtime evidence,
   consumer allowlists, task-wide restrictions and effort ceilings.
4. Introduce a new finding or phase while related follow-up work continues.
   Check profile reassessment, sensible reuse and consideration of other ready
   branches after defects, helper completion and before long waits. Helpers
   cannot accelerate an inherently serial external operation.
5. With Subagents Off, no helpers should start. With On, a trivial or tightly
   sequential task should complete directly without a minimum-helper rule.
6. Check findings against sources and validate the integrated result. Preserve
   admitted parent profiles, task permissions and independent review/publication
   boundaries. Where available, compare elapsed time, result quality and total
   usage; extra helpers are not proof of benefit or lower consumption.

Record checks and gaps through the consumer's existing process; no delegation
ledger or policy-maintenance service is required. Updating this package later
does not mutate an admitted task. Direct-copy integrations may select current
Landscape `main` when deliberately updating between tasks; a pinned flow remains
its installed snapshot until the consumer separately adopts another version.
A global reference must point to a policy file accessible to that client; a
project copy must include the complete policy in the consumer repository. Select
real host paths under consumer authority and verify them in a fresh session.
See the [package README](../../../README.md) for the version contract.
