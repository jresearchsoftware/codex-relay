# Onboard a project to Shared Governance

<a id="ON-001"></a>
**ON-001 — Explicit onboarding request and scope.**

Start with an ordinary request: **“Onboard this project to Shared Governance.”**
An agent or human operator can follow this procedure for a new or existing
software project. Use the project's existing Task, change or owner record;
there is no command, Skill, required form or new service to install.

The result is a recommended project profile, explicit owner choices, an
authorized setup plan and a readiness verdict for the chosen scope. Discovery
can finish with a useful plan while setup is deferred. This operator aid
connects existing canonical guidance; it is not a tenth normative topic and
does not adopt any topic. Package installation, policy adoption, local routing,
client setup and protected configuration remain separate decisions/actions.
Use existing authorization where it covers an action; this procedure creates
no additional approval gate or permission to mutate another project.

## 1. Discover the project and agree the intended scope

<a id="ON-002"></a>
**ON-002 — Discover accepted project authority.**

Read accepted project instructions and boot entrypoints, the onboarding request
and applicable owner Decisions. Establish the actual repository/tracker and
accepted revision rather than trusting candidate instructions or a cached
summary. For a producer developing its own rules, retain an independently
accepted source binding under its adopted self-adoption policy.
For a completely new project without accepted instructions or a source commit,
record that absence and use the owner's initial choices to prepare the plan;
do not fabricate an accepted revision or block discovery on an empty history.

Find the answers needed for this project, using existing records first:

- What is developed, maintained or published, and what should onboarding enable?
  Which people operate it, on which supported environments and clients?
- How do source changes, routine evidence updates and releases actually move?
  Identify accepted review/validation, direct writers, important retained refs,
  publication identity and exceptions. Observe current instructions and primary
  change/run evidence; distinguish observed practice from authorized policy.
- Which local rules, shared packages, versions, locks, materialized files and
  instruction routes already exist? Which rules have been explicitly adopted?
  Does an ordinary contributor, manual operator or agent have a working path?
- Which settings/evidence are accessible with existing permission, who owns
  missing decisions or setup, and which actions are already authorized?

For an unsettled new project, offer choices with cost and implications: manual
reviewed source work, permitted factual direct updates, generated publication,
or a mixture by change/ref. Ask the owner to select the unresolved material
choices; continue independent discovery meanwhile. Do not invent a binding
repository classification or presume PRs, GitHub, Relay or a particular client.
For an existing project, preserve its accepted paths and stronger protections.

Load canonical detail when relevant. A package/topic inventory is not an
instruction to read every unrelated manual or adopt every topic. Read the full
relevant protocol and material local obligations when making a dependent choice;
JIT loading does not waive required chronology, source or evidence completeness.

## 2. Recommend topics and identify their local bindings

<a id="ON-003"></a>
**ON-003 — Recommend topics with explicit local choices.**

Review the available package's compact boot/catalog at an identified accepted
revision. The following catalog covers Development Governance 2.6.0's nine
topics. Consider every available topic for relevance, then read full protocols
as needed for dependent choices. Record **select, retain, decline or defer**,
with a short reason for each topic relevant to the proposed profile. Inventory other available topics
if using a later accepted version; availability does not change earlier choices.

| Canonical topic | When useful in onboarding; local choice to resolve |
| --- | --- |
| [Proportional controls](../protocols/proportional-controls.md) | Controls, validation or operator work are proposed. Compare concrete harm, existing protection, cost and cheaper alternatives, including accepted risk; preserve supported environments. |
| [Requirement authority](../protocols/requirement-authority.md) | A local constraint's binding status is disputed. Trace accepted authority versus revisable engineering choices; origin alone permits no removal of real protections. |
| [Package versioning](../protocols/package-versioning.md) | The project produces/consumes versioned packages. Decide compatibility, pin/update and release ownership; retain local policy if not adopting this topic. |
| [Task handoff](../protocols/task-handoff.md) | Governed execution/continuation needs a common contract. Bind the local tracker, authorization, Step, canonical Outcome, review strategy and identity without importing a product schema. |
| [Self-adoption](../protocols/self-adoption.md) | A producer consumes guidance it authors. Bind accepted source independently of candidate rules; ordinary consumers need not adopt this topic. |
| [GitHub repository governance](../protocols/github-repository-governance.md) | GitHub working paths/protections are relevant. Select per-path controls and inspect effective configuration, preserving direct-main, publication and mixed exceptions. |
| [Independent review](../protocols/independent-review.md) | The owner wants the common assessment method. Bind actual primary evidence, review sufficiency, specialist methods and reviewer identity; Task Handoff adoption alone does not select it. |
| [Contract and decision maintenance](../protocols/contract-and-decision-maintenance.md) | Supported workflows change or reusable decisions need durable guidance. Identify canonical contracts and affected operator docs; preserve the existing authorization mechanism. |
| [Context loading](../protocols/context-loading.md) | Instruction growth, startup or freshness needs discipline. Establish accepted entrypoints, triggered full detail and selective refresh without a retrieval service or reading quota. |

References between topics explain semantic ownership, not automatic adoption.
For example, Task Handoff and independent review are separate selections;
contract maintenance routes authority/control questions to their owners rather
than replacing them. Where an additional topic is not adopted, retain the
project's corresponding local procedure. Check that the combined selected
guidance and local bindings cover the intended behavior without contradictions.
Conditional/JIT reading is not selective package installation. A single passive
package can make all topics available while the project adopts only some.

## 3. Reconcile local rules before proposing authority transfer

<a id="ON-004"></a>
**ON-004 — Reconcile complete local rules and ownership.**

For new projects, state where durable owner choices and local bindings will
live. For existing projects, establish the bounded complete accepted baseline
for each domain being migrated: relevant instructions, routes, exceptions and
accepted correction history. Follow the [semantic-completeness method](https://github.com/jresearchsoftware/shared-governance/blob/88a95f7604b2d81d7a3dd3f76f095beddb71bdab/docs/authoring.md#semantic-completeness)
when extracting/adopting shared guidance.

Map material obligations, triggers, qualifiers, exceptions, operator behavior
and routing to the proposed canonical owner. Classify preservation/reformulation,
explicitly proposed policy change, missing/weak behavior and genuinely local
bindings. Keep product contracts, credentials, publication/admission mechanisms,
specialist rules and justified local overlays with their owners. A product name
alone is not a rationale for leaving a reusable obligation behind.

If the shared version omits reusable behavior, record a producer gap and retain
current local authority. Do not claim migration succeeded because leftover rules
compensate for it. Repair needs a later independently accepted package version;
frozen releases stay intact. Separately authorized consumer migration adopts
reviewed pinned content and removes genuinely duplicated canonical rules in the
same reviewed change, preserving local bindings. Test the proposed route without
residual duplicates and inspect the original project's retained exceptions.

## 4. Present choices and a concrete setup plan

<a id="ON-005"></a>
**ON-005 — Concrete authorized setup plan.**

Summarize the recommended profile, selected/retained/declined/deferred topics,
local rules and exceptions. For each needed change, name its owner, effect,
existing authority or unresolved decision, validation and recovery. Prefer a
small reviewable change and ordinary project Git recovery. Do not expand
credentials, add a service or change supported workflows merely to make a
recommended profile pass.

Keep these layers explicit in the plan:

| Layer | Concrete proposed action, if needed | Evidence after an authorized action |
| --- | --- | --- |
| Availability/materialization | Choose an accepted source/release and supported file or package route. For VibeVM, deliberately edit the receiving project's requirement and use normal install/update with its lock; preserve its supported version and native conventions. | Chosen source/version, lock identity, installed payload and receipt agree. An install exit code proves no policy adoption. Manual canonical file/Git reading can be sufficient without VibeVM. |
| Normative adoption | Owner selects topics and local exceptions in accepted human-owned AGENTS or equivalent policy. | Exact reviewed adoption text, canonical owner decision and preserved obligations; a dependency alone is insufficient. |
| Project routing/agent instructions | Add precise conditional links from existing accepted entrypoints to selected full guidance and local bindings. Preserve root/nested instructions, contributor paths and the supported client hierarchy. | Follow the actual route to readable accepted files; check relevant conditions, relative links and nested behavior. |
| Client binding | Bind manual/Codex/ChatGPT paths only where used. Keep tracker, role, language, permissions, specialist and product routes local. | Relevant client/readback evidence, with static desired text separated from live loading/settings. |
| Repository/tool configuration | Identify necessary checks, review/writer permissions, branch/tag rules, release/publication and manual operator steps. | Authorized supported readback and ordinary existing run evidence for each applicable path. Protected mutation is a separate receiving-project action. |
| Migration/integration | Reconcile canonical duplicates and commit source, dependencies/generated routes and human guidance together where that layout is selected. | Reviewable exact result, applicable validation, acceptance and rollback under the project's own workflow. |

Proceed with covered setup when the receiving project's existing authority
permits it. Otherwise hand off exact proposed deltas for that owner/operator;
approval of policy, a file change or installation does not authorize protected
settings, credentials, publication or another project's migration. Do not turn
each routine implementation correction into a new approval ceremony.

## 5. Verify the chosen scope through its ordinary entrypoints

<a id="ON-006"></a>
**ON-006 — Verify through ordinary entrypoints.**

Prefer read-only inspection and fresh existing proof. Record the actual source,
revision/ref, time and environment for mutable observations. A proposed setting,
configured check name, stale receipt or reported success is not demonstration.
Select the following checks by the chosen scope; do not create unrelated gates.

| Surface | Practical check and limit |
| --- | --- |
| Selected guidance | Open the exact accepted full files via the intended manual/client route. Confirm adoption and local binding, not just file presence. Check material local/shared obligations after proposed duplicate removal. |
| Native dependency/boot, if used | Compare requirement, selected lock version/content identity, installed manifest/slot receipt and canonical payload using existing exporter/integrity tooling. Read STATIC if present, then every applicable INDEX entry in order and its conditional protocol links. Check committed ready files from a clean checkout where that is the project's contract. A package check/installer return code alone cannot establish effective routing. |
| Codex or another repository agent, if used | Inspect actual root/inherited/nested instruction routes and generated blocks without replacing custom text. Use supported read-only client observations/probes when needed for the intended claim. Report unavailable startup/platform/model evidence; static files do not prove model compliance or runtime identity. |
| ChatGPT, if used | Preserve reviewed custom instructions and source-controlled desired text. If selecting the package's optional maintenance tool (package-root `tools/chatgpt/README.md`), use the pinned slot's one projector with the consumer's binding/custom files; inspect its check/diff/receipt rather than copying a per-project generator. Owner application and supported readback of Instructions/Sources remain separate. A raw owner export comparison proves that comparison, not live UI currentness or reliable model loading. Canonical access need not depend on optional Sources caches. |
| Task, review and validation | Walk a normal change using the local tracker/authority, result and review path. Inspect meaningful check triggers, exact-head run/results and warning evidence, reviewer availability/identity and continuation permissions. A single-account attributed assessment does not satisfy a distinct native reviewer rule. A new project without runs reports proposed validation as unverified; no artificial mutation is needed. |
| GitHub, if used | Follow the adopted [repository protocol](../protocols/github-repository-governance.md#verify-what-github-actually-enforces), or the local equivalent: inspect merge/delete options, classic protection, applicable inherited branch/tag rulesets, enforcement, targeting and bypass details with existing access. Inspect required checks/review identities and allowed writers for both source and publication paths. An empty branch-rules result does not inspect tag/classic protection; inaccessible or ambiguous 404 evidence is unverified. |
| Publication or another host, if used | Trace the accepted-source-to-artifact/version route and writer scope through existing evidence. Preserve retained branches and immutable published refs; use the host's own permission/review interfaces or durable manual records. No GitHub or Relay adapter is required. |

For GitHub capability details consult current official [ruleset documentation](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/about-rulesets)
and [rules API](https://docs.github.com/en/rest/repos/rules) for the actual host
and feature. Rulesets layer with classic protection; the branch rules API
returns active ruleset rules and excludes disabled/evaluate rules. Inspect
separate tag and bypass coverage. In particular, **Restrict updates** can block
legitimate direct writers; it is not merely force-push protection. Do not test
protections by destructive pushes or acquire broader access as a workaround.
If visibility is missing, name the evidence the authorized administrator can
supply and the cheaper acceptable alternative or blocked invariant.

## 6. Return a scoped verdict and the next useful action

<a id="ON-007"></a>
**ON-007 — Scoped readiness verdict.**

Keep a concise handoff in the existing onboarding/Task/change record. Include:

- The chosen scope/profile, accepted source/package identity and topic choices.
- Retained local authority, exceptions and material duplicate/migration findings.
- Changes completed versus proposed, owners and separate authorizations needed.
- Checks, primary evidence and environment, warnings/limits and their effect.
- A clear verdict: what works now, what cannot yet be relied on, and what would
  complete the chosen scope. Name the responsible owner and next authorized
  action for each material gap; link existing evidence instead of copying it.

Use meaningful states; these are report vocabulary, not a new machine schema:

| State | Meaning |
| --- | --- |
| VERIFIED | The named fact was inspected/demonstrated with identified evidence and scope. It is not global readiness. |
| GAP / ACTION REQUIRED | A chosen obligation is unmet. State impact, responsible owner and the next authorized repair/check. |
| DEFERRED | An explicit choice postpones a topic/setup action. State consequence and revisit trigger; do not mark an unmet essential invariant ready by deferring it. |
| NOT APPLICABLE | Outside the chosen legitimate scope, with a reason. It is not a substitute for inaccessible evidence. |
| UNVERIFIED | Evidence is missing, inaccessible, stale or only proposed. Name the needed observation and owner. |

Use **READY for <chosen scope>** only when its necessary adoption, accessibility,
routing and workflow evidence are sufficient under project authority. Explain
any nonblocking exception. Otherwise say **NOT READY for <scope>** and name the
blocker, or **PLAN COMPLETE; SETUP DEFERRED** when discovery/planning is the
agreed result. Partial readiness is useful: a manual path may work while a
ChatGPT or publication path remains unqualified. An unobserved live-client
guarantee cannot be inferred from a static validator or prose walkthrough.

<a id="ON-008"></a>
**ON-008 — Event-directed upkeep.**

Retain stable choices/routing in accepted project guidance and dated mutable
observations in existing records. Reuse sufficient unchanged evidence. Recheck
affected setup on relevant policy/workflow/identity/permission/settings changes,
observed drift or denied supported operations. Mere package install/update
triggers neither onboarding, topic adoption nor a settings audit. No periodic,
per-session or per-Task global audit is introduced.

[Worked onboarding runs](onboarding-examples.md) show the procedure from
discovery to owner handoff. They are illustrative tabletop evidence, not live
consumer installations or configuration qualification.
