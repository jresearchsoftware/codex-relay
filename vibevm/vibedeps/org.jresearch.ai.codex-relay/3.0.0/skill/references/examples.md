# Human authoring and walkthroughs

All repositories, numbers and activities below are synthetic. These examples
illustrate decisions and visible meaning, not live admission or complete API
payloads. Use the compatible connected tool and, after assembly, read the
bundled exact v4 schema `product/github-authority-v4.json` for typed records. Do not paste
fictional native IDs, hashes or result evidence into a real request.

## Normal Task

An owner creates Issue #42 in `example-org/sample-project`:

```text
Authority model: github-native-v1

Problem: Export retry can duplicate a completed record.
Goal: A repeated export preserves exactly one completed record.
Scope: Correct retry bookkeeping and test the affected export behavior.
Boundaries: No deployment, credentials, settings or consumer repository changes.

Issue closure policy: close-authorized
Completion and closure require development, independent exact-head source
acceptance, merge and explicitly authorized read-only representative consumer
qualification, with no remaining work or hold. No consumer mutation is authorized.
```

Issue creation supplies no Step and starts no worker. If the owner accepts a
durable scope clarification, publish a trusted v4 Task Decision expressing that
delta. Do not rewrite the stable charter or duplicate it in a public Request.
Apply `codex-ready-auto` for governed repository work or
`codex-ready-manual` for an authorized manual route. Writer resolves and
records the admission, including Step and starting state.

A manual handoff can remain short while preserving the actual admitted prompt:

```text
Task 42 — Step 1 — Correct export retry bookkeeping
Canonical authority: https://github.com/example-org/sample-project/issues/42
Use the supplied Writer admission/handoff and its exact source references.
Implement and validate within its scope; preserve useful work and report limits.
```

Here Step 1 represents an assumed successfully admitted first execution, not an
author-assigned future Step. Copy the real identity/profile from the actual
handoff. Client naming/readback follows supported consumer instructions;
successful text generation alone does not prove a persisted rename.

## CR and the next execution

An independent review of exact PR #43 head finds that retry failure clears the
completed-record marker. Record the candidate and comparison SHAs, triggering
case, impact, evidence, provenance, bounded correction and acceptance evidence.
Publish a native v4 `REQUEST_CHANGES`/`change-request` bound to that PR/head.

The CR carries no future Step and creates no replacement Task Request. Owner
orchestration verifies Writer's exact CR/head Draft transition, then applies the
matching ready command to PR #43. Writer admits the next execution and supplies
its Step. Keep the branch, PR and starting-head binding. Inner corrections and
tests stay in that execution. A new candidate requires fresh exact-head review.

If the suggested correction instead changes the authorized export workflow,
surface the material owner choice in canonical authority before implementing
it. A review finding cannot enlarge Task scope by itself.

## Source result and one Outcome

The executor preserves a substantive candidate commit on the admitted branch,
reports affected checks and distinguishes local test claims from native CI.
A Relay-admitted manual session submits the complete Outcome claim using
`submit_manual_outcome`; automatic workers hand commits/claims to Writer.

Useful visible result prose says what changed, identifies the exact full head,
describes evidence and limitations, discloses warnings/residue and requests the
independent review boundary. Writer publishes the single canonical Outcome on
the uniquely bound PR. Do not add a second Issue result-copy comment or a
PASS-only CI update. The protected binding and machine block come from the
compatible publisher, not a hand-maintained example.

## Legitimate no-PR qualification

Suppose separately admitted manual work qualifies the accepted export behavior
without changing source. Its result can identify an immutable qualification run
and bounded native check/result IDs. Do not create an empty commit, invent a Git
head or keep an artificial PR open merely to obtain a review surface.

Writer publishes one Issue Outcome, or preserves its exact already-bound
disposed qualification artifact according to the admitted contract. Independent
Issue `task-approval` accepts the exact Writer Outcome, authority/admission and
immutable result, preserving warnings and limitations. It grants no PR merge
permission. Unavailable installation/production evidence remains unavailable.

## Explicitly authorized standalone source PR

Suppose Issue #42 explicitly authorizes standalone manual implementation and
its owner-created PR #43, and no Relay attempt was admitted for that result.
The executor publishes the exact source head, validation evidence, ordinary
owner Outcome and limitations through the authorized owner channel. It invents
no admission, Step, ready event or Writer receipt.

An independent evaluator reviews the full candidate against current canonical
authority and warning evidence. The qualified Reviewer publishes native
exact-head `APPROVE`, binding the verified owner-created source PR and current
authority. An owner-account review or copied assessment does not replace that
native proof. The trusted owner channel verifies explicit standalone permission,
absence of an admitted attempt for this result, warnings, passing required
checks, mergeability, holds and `closesTask: false`, then can perform the
already-authorized squash without another confirmation. It uses neutral merge
text and verifies the native merged result. No ordinary owner result becomes a
Writer Outcome or Task Approval.

If execution markers instead show that PR #43 is a Relay-admitted result, retain
its original Writer publication/recovery requirements. Missing automation does
not turn it into standalone work. If the merge response is uncertain, reconcile
the reserved action with native readback before dependent work. Do not repeat
the merge or launch another execution. Issue #42 remains open while its stated
qualification work remains.

## Review, continuation and closure

An independent evaluator reviews the complete PR #43 candidate against current
Task authority, relevant behavior and warning evidence. Native exact-head
approval is distinct from both the evaluator's judgment and the owner's
authorized continuation. A copied owner-account assessment cannot replace
Relay's native Reviewer identity. Do not approve your own implementation.

After acceptance the owner path verifies live head, required checks, readiness,
holds, current authority and protected boundaries before any already-authorized
integration. A source merge does not complete the consumer qualification in
Issue #42's remaining-work condition. Keep it open.

After the specified qualification and all other completion conditions pass,
the existing owner continuation verifies acceptance, no remaining work/hold
and protected boundaries, then closes under the charter's `close-authorized`.
No second closure permission or redundant Decision is needed. A CR, Outcome,
Step completion or merge alone cannot establish Task completion.

Use `keep-open` instead when a concrete qualification choice, extra work or
closure hold remains outside the authorized path; state that condition. If the
owner later defers, combines or cancels a required qualification/Apply, amend
completion conditions and closure authority through a trusted Task-scoped
Decision without rewriting the admitted charter or claiming it happened.

## Capability mismatch and retained history

If a new Relay-admitted manual v4 session cannot see `submit_manual_outcome`, preserve its work
and report the missing connected capability and qualified installation needed.
Do not substitute an owner result comment or a new v3 Request.

An already-admitted v3 attempt is different: use its exact original complete
Request, references, Step, result transport and recovery contract. Leave those
historical bytes intact. Neither that retained path nor installing this Skill
authorizes a fresh old-style execution on a qualified v4 installation.
