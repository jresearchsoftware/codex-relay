# Development governance

<a id="DG-002"></a>
**DG-002 — Conditional topic routing.**

For proposed security, validation or operator controls, read the full
[proportional-controls protocol](../protocols/proportional-controls.md),
including when assessing behaviorally free security hardening. Unrelated tasks
do not require reading it. Apply shared guidance within the owning project's
current scope and authority; it grants no authority to launch Tasks, publish,
review or adopt guidance for another consumer. Consumers separately review and pin updates.

When deciding whether an earlier requirement binds newly authorized work,
read [requirement-authority](../protocols/requirement-authority.md) when relevant
under the owning project's adopted guidance. Proportional-controls routes its
own relevant provenance decisions there; a project may separately adopt that
common rule for other domains. It does not activate a contract-review flow,
supersede local authority or require provenance work on unrelated tasks.

For package lifecycle work, read [package-versioning](../protocols/package-versioning.md)
only when the owning project has explicitly adopted that topic through its
human-owned AGENTS or equivalent policy. Installing or updating this package
does not activate that protocol or replace pre-existing local versioning rules.
Newly adopting projects select their route in their own accepted guidance;
unrelated tasks skip it. Conditional reading does not selectively install clauses.

For governed task execution, handoff or continuation, read
[task-handoff](../protocols/task-handoff.md) only when the owning project has
explicitly adopted it through human-owned AGENTS or equivalent guidance.
Installing/updating this package does not activate the topic or replace local
Task authority, authorization, review or execution mechanisms. Adopted bindings
implement its shared Step semantics and selected acceptance strategy. Unrelated tasks
skip it; client adapters and product-version compatibility remain project-owned.

Where a producer consumes guidance or Skills it authors, read
[self-adoption](../protocols/self-adoption.md) only when its owning project has
explicitly adopted that topic. Develop/review under identifiable independently
accepted source-main guidance; candidate rules remain proposals. Ordinary native
materialization, committed ready files and conditional reading preserve project
overlays and local authority. Other repositories and unrelated work skip this
topic; package installation or update does not activate it.

For GitHub repository onboarding, workflow or protection-policy decisions, read
[workflow-aware repository governance](../protocols/github-repository-governance.md)
only when the owning project explicitly adopts that topic. Preserve its accepted
PR, direct-main, publication and mixed paths; installing/updating guidance neither
applies settings nor grants permission to change them. Existing local policy
remains authoritative until reviewed adoption. Unrelated tasks skip this topic.

For independent assessment, read
[full independent-review methodology](../protocols/independent-review.md) only when
the owning project explicitly adopts that topic. Inspect the actual result and
primary evidence; disclose review gaps before a positive verdict. Package updates
and Task Handoff adoption do not activate this additional topic. Local acceptance
authority, specialist methods and stronger identity requirements remain intact;
unrelated tasks skip it.

For material user/operator contract changes, accepted decision promotion or
affected workflow documentation, read
[contract and decision maintenance](../protocols/contract-and-decision-maintenance.md)
only when the owning project explicitly adopts this topic. Existing local rules
and the other topics' applicability remain intact; installation/update does not
activate it. Unrelated tasks skip it.

For selecting, loading or refreshing work context, read
[context loading and JIT discipline](../protocols/context-loading.md) only when
the owning project explicitly adopts this topic. Start with decision-relevant
authority, load canonical detail when triggered and refresh affected mutable
facts without weakening required completeness. Existing topic adoption,
entrypoints, contributor paths and client instruction hierarchy remain intact;
installation/update does not activate it. It adds no runtime retrieval or boot
command and grants no new authority.

For capturing deferred small source corrections and preparing the first suitable
authorized source-changing Task, first source-changing Step after analysis,
relevant CR or new source-changing PR opportunity, read
[small improvements](../protocols/small-improvements.md) only when the owning
project separately adopts that topic. Use its exact Issue label for discovery
and automatically include all bounded eligible same-repository candidates under
that adoption's standing delegation, without per-candidate permission or advance
notification. Topic similarity and necessity to the main goal are not eligibility
gates. Preserve explicit current Task exclusions, protected actions and admission;
the delegation does not launch Tasks or transfer authority to other projects.
Installation/update, Task Handoff adoption and this route do not activate it.
Analysis-only work skips its scan; broader accepted local planning rules remain.
Do not scan per internal commit or disturb an already approved PR solely for
minor additions. Use the normal combined exact-head independent review and keep
provenance, concrete deferrals and unfinished work discoverable.
Its [usage guide](../guides/small-improvements.md) illustrates deliberate adoption
and separately authorized consumer deduplication. Unrelated tasks skip it.

When a person explicitly requests project onboarding, for example “Onboard this
project to Shared Governance,” read the [onboarding procedure](../guides/onboarding.md).
Skip that detail in ordinary sessions and on package install/update alone.
This operator aid adopts no topic and grants no configuration-change authority.

When guiding a human through shell or administrative work and requesting a
return result, read [human command interaction](../protocols/human-command-interaction.md)
only when the owning project explicitly adopts that topic. It covers ordinary
diagnostics/setup as well as governed work: one self-contained human action and
one coherent report, batching safe commands while stopping at interpretation,
choice, permission or safety boundaries. Its [Bash and PowerShell examples](../guides/human-command-interaction.md)
illustrate copyback and failures. Installation/update, Task Handoff adoption and
this route do not activate it or serialize autonomous agent tool calls.
Existing local authority and stronger boundaries remain; unrelated work skips it.

When external engineering or reasoning methods would materially help the current
work, you may consult the [optional FPF guide](../guides/engineering-methods.md).
Skip it when existing methods/evidence suffice; startup or install/update alone
never require the guide, FPF access or MCP. FPF advice grants no project authority.
