# Warnings, blocked work and recovery

Use this reference when execution evidence or an uncertain operation affects
the next decision. Diagnosis remains within the admitted goal and actual
permissions. A Skill is not access to protected logs, credentials or services.

## Inspect supported warning surfaces

Before independent review, continuation, merge, closure or a material owner
decision, inspect applicable execution-time Writer Outcomes, native job/check
annotations and Relay/controller/Actions annotations associated with the attempt.
A green run does not dispose of a warning. Searching logs for the word
`warning` does not replace these primary surfaces.

For a PR, `read_pr_review_evidence` uses only `{repository, pr_number,
expected_head_sha}`. It verifies the binding before and after bounded read-only
collection. Preserve the distinction between reviewed candidate head and actual
execution head: an exact-head Outcome's native `Attempt: run-N` can bind a
routing run executed on the trusted base.

The evidence reader distinguishes available, absent, unavailable,
permission-denied and truncated sources. Required supported source failure
prevents an absence claim. `required_surfaces_complete` and `none_observed`
describe only the supported acquisition scope; neither is acceptance.

GitHub service/pre-execution UI-only banners are excluded from mandatory
automated acquisition until a suitable supported API exists. The excluded
source alone does not block review or make supported evidence incomplete.
Do not scrape HTML or use browser cookies/session state as a fallback. A
material warning already known from any evidence still needs disposition.

Record each material warning's source, impact, relation to scope, resolution or
remaining limitation, next action/owner where applicable, evidence gaps and
effect on the current decision. Preserve all Outcome limitations. Report an
unavailable required surface explicitly, without claiming no warnings exist.

## Claims and protected diagnostic evidence

Writer verifies bindings and publication; executor validation summaries remain
claims unless independently evidenced. Launcher/dispatcher/Git exit or signal
does not establish the inner Codex result. Actual model/effort and usage stay
unavailable when original runtime evidence does not expose them. Native token
counters are session-total observations, not billing proof.

Public Outcomes can expose bounded categorical causes, inner-start/exit/signal
observations, stderr byte-count/truncation and diagnostic availability. Raw
streams, protected paths, store references and diagnostic previews stay
protected. Never widen access or copy protected data into a public comment to
improve a report. Missing observation is not proof of successful containment.

## Stop, preserve and reconcile

Continue useful safe diagnosis while its next action is clear. Stop for an
owner decision, uncertain scope/permission, unknown/uncontained prior execution,
ambiguous external mutation or repeated failure without new evidence. Preserve
useful source in substantive commits/artifacts, keep unrelated work intact and
state local residue plus its safe publication/access boundary.

A contained durable success can be `COMPLETED_WITH_WARNINGS` with
`UNCOMMITTED_WORK_REMAINS`. This is a mandatory next-review input, not proof that
residue is disposable or accepted. Unknown collection, containment, authority,
evidence or publication remains a failure. Do not discard/commit arbitrary
bytes, widen permissions or launch another worker to make status green.

Publication recovery reconciles the same reserved operation, native marker,
exact body/digest and original target. Read back uncertain POST/push outcomes;
do not blindly repeat mutations, replace a PR, infer no publication from a
missing response or re-execute Codex. A replay retains the attempt and Step.
A genuinely new execution after terminal BLOCKED needs new owner admission and
receives a new v4 Step.

Missing automation stops only the operation requiring that capability; any
otherwise authorized standalone route still follows the
[manual's route and continuation rules](workflow.md#owner-acceptance-and-execution-routes).
It cannot resolve unknown execution, conflicting refs or external effects, or
substitute for an admitted attempt's result/recovery. Owner continuation also
reconciles reserved merge/closure/launch operations from exact native readback;
an uncertain response never authorizes a repeated mutation or another launch.

Report a blocker with established facts, eliminated material hypotheses,
remaining uncertainty, preserved work, available safe actions, the exact
authority/capability boundary and the next owner action. Relay repository-only
developer stop hooks and their conditional technical-blocker fields are local
development aids; they are not universal consumer admission or recovery gates.

Runtime capsule retention/disposal and deployment recovery use their existing
protected operational entrypoints and owner authority. No arbitrary diagnostic
read/delete or cleanup is granted here. An explicitly isolated disposable TEST
sandbox follows its admitted TEST policy; uncertainty about its boundary stops
outside effects and does not grant production control.
